2. 原二级页在同一动画事务里切换条件分支、初始化表单和回填材质高度，补卡初始化还启动了另一轮布局动画。现在先在屏外完成布局，再用一次原生属性动画修改位移与透明度；转场期间启用合成缓存，完成后恢复实时材质，退出完成后才卸载子页。详情保留滚动位置，过期帧回调和预布局期间返回均有保护。补卡初次选择日期直接初始化，用户后续选日仍播放动画。

## 后续反馈：材质闪现与动画绘制帧率

用户真机反馈：进入编辑、补卡时四个管理按钮闪现，补卡分区背板延后出现；转场不像掉帧，而是以较低绘制帧率播放。首轮静态布局与操作回归未覆盖这一瞬态问题。

定位与修正：

- 两个页面原先使用 `renderGroup(navigationMoving)`，在动画开始和结束切换整页离屏缓存。普通静态内容的缓存优化不适合这些需要实时背景采样的原生材质；详情整体透明度还在同时变化。两层现始终使用 `renderGroup(false)`，保留两帧预布局和单次原生变换动画，不用纯色蒙版或截图替代材质。
- `animateModal` 原先未设置 `expectedFrameRateRange`，按应用默认帧率执行。现在查询 `display.Display.supportedRefreshRates`，只为本次进出动画请求设备支持的最高帧率。避免用静止页面当前的 `refreshRate` 把高刷屏限制到 60；能力列表空缺或查询失败时请求 120，由系统按设备能力与调度策略处理。没有修改应用或系统全局刷新率。
- 保留既有补卡底部静态渐隐。本次先移除新增的整页缓存切换；原生 `fadingEdge` 也使用 OFFSCREEN，不能当作可靠的材质兼容替代方案。

npm CLI 文档依据：《图像效果》明确 `renderGroup` 离屏缓存及整体透明度的绘制差异；《显式动画》说明默认帧率和 `expectedFrameRateRange`；《屏幕属性》列出 API 20 的 `supportedRefreshRates`。

本轮导航 105、打卡视图 152、补卡 72、材质 48，共 377 项断言通过。导航包含 60/90/120/144Hz 能力、当前 60Hz 但支持 120Hz、无效能力列表与查询异常，以及转场开始/中途/结束均保持实时材质的验证。Release 签名构建成功。

帧率参数是向系统提出的绘制请求，不能用它或屏幕显示 120Hz 的读数证明实际每一帧的渲染速率；真机连续材质效果仍需结合实际显示观察。
